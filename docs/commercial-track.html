NS-COM-101 / 102 · APPSEC · 5–8 HOURS

Account authorization and search security

Ticket: An account lookup allows one fictional customer to view another customer’s account. A separate search endpoint interpolates request data into SQL. Diagnose both defects and implement a regression-tested fix.

What you build: A corrected Python/SQLite backend supporting actual localhost HTTP requests and safe, owner-scoped account lookups.

cd labs/commercial-api-security
bash run-checks.sh        # fails on starter defects
python3 src/api.py --port 8080

The server binds to 127.0.0.1. The demo persona header is not authentication, and the account data is invented.

Architecture decision · broken object authorization

A GET /api/v1/accounts/202 call carries the demo identity alex, but account 202 belongs to blair. What should the backend do?

Code review · parameterized query

Which approach prevents the search term from changing SQL structure?

NS-COM-201 / 202 · BACKEND SECURITY · 5–8 HOURS

Transaction integrity and safe retries

Ticket: A duplicate delivery transfers funds twice. Another defect commits a debit before its corresponding credit and ledger record, breaking integrity when processing fails.

What you build: A retry-safe, atomic synthetic transfer service with SQLite transactions, idempotency keys and failure-injection regression tests.

cd labs/commercial-transaction-integrity
bash run-checks.sh        # fails on starter defects
python3 src/cli.py --db /tmp/ns-demo.sqlite3
Architecture decision · idempotency

The same request ID is retried with identical transfer details. What's the safest intended behavior?

Fault analysis · partial failure

What should happen to debit, credit, audit record and request record if a failure occurs midway?

Engineering residency protocol

1. Read the ticket and inspect the baseline behavior. 2. Reproduce with synthetic data. 3. Write regression tests. 4. Implement and review the fix. 5. Submit evidence and a concise risk assessment.
